# 硬约束与实测数据

本文件是「为什么默认参数是这些值」的证据台账。**改默认值之前先读这里**——下表每一行都是实测出来的，不是估的。

## 一、两条硬上限（决定了整个技术路线）

| 限制 | 值 | 出处 |
|---|---|---|
| Photoshop「存储为 Web 所用格式（旧版）」/ 切片导出高度上限 | **30000 px** | CS6 起沿用至今，超限时菜单变灰或导出中断 |
| 浏览器 canvas 最大尺寸 | **16384 px = 2¹⁴** | 绝大多数 GPU 的纹理尺寸上限，canvas 由 GPU 光栅化 |

**推论**：实测素材 750 × 33744px（16.8MB，2530 万像素，内存展开约 72MB）。
- 高度 33744 > 30000 → **PS 切片导出失败的真正原因**。PS 画布本身装得下，失败的只是那条独立导出通道。
- 33744 > 16384 → **「在第三方网页平台切长图」这条路物理上不成立**，换任何在线工具都一样。

**唯一正解**：运算放本地 CPU（72MB 毫无压力），浏览器只负责显示与输入；预览不能用 canvas，改用多个 `<img>` 分块堆叠（每块 ≤5000px）。

## 二、JPEG 配置实测（对最坏切片：2646px 高）

| 配置 | 体积 | PSNR | SSIM |
|---|---|---|---|
| q100 4:4:4 baseline | 1.83MB | 56.3 | 0.9997 |
| q100 4:4:4 progressive | 1.75MB | 56.3 | 0.9997 |
| **q96 4:4:4 progressive** | **0.95MB** | **43.3** | **0.9968** |
| q95 4:2:0 progressive | 0.64MB | 34.9 | 0.9878 |

**结论一**：q96+4:4:4（0.95MB / SSIM 0.9968）优于 q95+4:2:0（0.64MB / SSIM 0.9878）
→ 策略必须是「**降 quality、死守 4:4:4**」，不是「保 quality、牺牲色度」。

**结论二**：progressive 比 baseline 同质量小 4–5%，PSNR/SSIM 完全一致 → **纯免费收益**，已设为默认。

**结论三**：「1M」口径有歧义（1,000,000 还是 1,048,576 字节）。按小的取再留 2% 余量（`SAFETY = 0.98`），两种口径都安全。

**实现**：对每片二分搜索「不超过上限的最高质量」（体积随 quality 单调递增，5–6 次编码收敛）。**已在上限内的片不碰**——实测 22 片里只有 8 片触发压缩（质量降至 95–99），其余保持 100。

**已核对的历史数字（与上表同源）**：23 片版本实测切片合计 20.69MB，单片 0.26–1.83MB；拼接还原平均绝对差 0.1054、最大 4、差异>30 的像素占比 0.00000%。

## 三、切点算法实测

### 空白分隔带检测参数
`行内 std < 0.8` 且 `跨行差 < 0.5` → 「安静行」；连续 **≥6px** 记作一条候选带。（实测素材上得 186 条候选带）

### 切点分数 = 留白宽度（层级信号）

用户指出要区分**大标题**（PC TOOL 智控中心 / OLED CARE+ 防烧屏）与**小标题**（像素移动 / 静态屏幕检测 / ISP 静态图标检测）。实测：

| 位置 | 上方留白宽度 |
|---|---|
| 大标题（Y=21916 字高 44、Y=25756 字高 44） | **143px / 128px** |
| 小标题（Y=21257 / 22653 / 23209 / 25125…，字高 31–37） | **7–27px** |

**5 倍以上差距**。而用户抱怨的「碎条区」刀位全部落在 **7–27px 的极窄带**上、且紧邻小标题
→ 「切太细」＝ **在小标题之间的窄留白下刀**。故「优先最宽留白」等价于「优先切在大标题之前」。

**为什么不用字号做判据**：字号确实可测（大标题 43–55px / 小标题 31–37px / 正文 20–24px），
但**分位区分度不足**（大标题 P97–99、小标题 P88–92），阈值不通用 → **弃用**，改用留白宽度这个更稳的信号。

### min_h 参数扫描（实测素材）

| min_h | 片数 | 最矮片 | <800px 片数 |
|---|---|---|---|
| 800 | 26 | 839 | 0 |
| **1000** | **22** | **1041** | **0** |
| 1200 | 19 | 1216 | 0 |
| 1600 | 14 | 1631 | 0 |

参照系：用户手工切的 22 刀 → 23 片、最矮 961px、无碎条 ⇒ 隐性底线约 **950–1000px**。
→ **默认 min_h = 1000**。

**为什么必须设 min_h**：只在候选间设固定 250px 间距会产出碎片（实测出过 **53px** 的尾巴）。

### 自动识别的能力上限（别指望它全自动）

按带长降序贪心取前 N 条（间隔 ≥250px）对比用户手工 22 刀：
**N=22 时召回 63.6%、准确 63.6%**。

原因：用户有些刀位（Y=1285、27307、28268）是**模块直接相接、没有空白带**，算法无从判断。
→ 定位为**助手**，不替代判断。真正有效的效率改进不是「全自动」，而是**消除精确定位的摩擦**（点击时磁吸到最近分隔带中心）。

### 切割点质量预检（值得固化的标准动作）

用相邻行差分的绝对均值作「纹理强度」，全图基准：中位 **4.56** / 75% **11.35** / 90% **18.61** / 99% **42.88** / 最大 **226.03**。

**判据：切点纹理强度 ≥ 全图 90% 分位 → 该刀切在密实区，会产生可见接缝，须提示用户复核。**

实测结果：**21/21 刀全部落在完全平坦行**（跳变强度 0.00），零接缝风险。22 片全部 ≤1MB（最大 0.94MB）。

## 四、已知限制

- 自动识别**只覆盖有留白的位置**，对模块直接相接的刀位无能为力。
- JPEG 无严格无损；「无损 jpg」只能理解为 quality=100 + 4:4:4 + optimize。要严格无损须 `--format png`。
- 启动时从磁盘读入的那张图，路径是**那一刻**的绝对路径；图被移动后 API 返回「找不到文件 <旧路径>」。错误提示清晰，且现在**直接在页面上换图**即可，不必改配置重启。

## 五、换图与输出布局（2026-10-12 第二轮改造）

### 输出从「平铺」改成「一图一子目录」

原设计把切片全部平铺在 `桌面\切图`。一旦要复用（切第二张图），第一张的切片会**残留**在目录里，
而「打开目录 → 全选 → 上传」会把两张图的切片一起传上去。
`clean_stale()` 只清**同名前缀**，对另一张图的名字无能为力 → 这是**静默错误**，比直接报错危险。

三种候选做法：

| 做法 | 判定 |
|---|---|
| `桌面\切图\<图名>\` 每图一子目录 | **采用**。互不污染，且「打开目录 → 全选 → 上传」动线完全不变 |
| 平铺，切新图前自动清空整个目录 | 否。会**静默删掉**上一张的成果，不可逆 |
| 平铺，只在结果里提示残留 | 否。依赖用户每次都读提示——提示被忽略就失效 |

### 图片改为可选：启动不再被某一张图绑架

`main()` 原先在找不到图时直接 `SystemExit`。现在图不存在就进「选择长图」起始页，
**先在浏览器里把服务开起来**，选图是页面内的事。这是从「只能切这一张」变成「通用长图切图工具」的关键一步。

### 上传路径为什么不经过 canvas

`<input type=file>` 拿到的是可读的 `File` 对象，直接把字节 POST 给本地服务器是最短路径
（浏览器出于安全不给页面本地真实路径，所以「让服务器读路径」做不到）。
**整条链路不触碰 canvas**：浏览器只搬字节，解码全在本地 Pillow → 16384px 的 GPU 纹理上限
在这条路上根本不构成约束。请求体按 1MB 分块**流式**落盘，不把整份文件堆进内存。

### 「换图不重启」的前提条件（架构约束，勿破坏）

`build_session(src, out_root, **opts) -> cfg` 是所有图相关状态的**唯一构建入口**：
读尺寸 → 扫分隔带 → 生成预览块 → 生成页面 HTML，全部塞进一个 `cfg` 字典；
服务器只持有 `httpd.cfg`，换图就是**换掉这个引用**。

> **任何新加的图相关状态都必须放进 `cfg`。** 一旦有变量漏到外面变成全局量，
> 换图时它不会更新，就会残留成上一张图的值——这类错最难查。

前端 `input[type=file]` 拿到 File 后 POST `/api/upload`（头带 `X-Filename`，**必须百分号编码**：
HTTP 头只能承载 latin-1，中文原名直接塞会编码失败），成功后 `location.reload()` 拿新页面。

### 验证证据（`test_upload_flow.py`，38 项全通过）

真起服务、真发请求、真读回页面，不读代码：

- 无图启动 → 起始页；无 token 调 `/api/slice`、`/api/upload` → 403；未选图就切图 → 明确中文提示
- 上传 1600×9000 → 尺寸/分隔带/输出子目录三项都对；页面标题、`原图 1600 × 9000 px`、`BANDS` 全部更新，占位符零残留
- 一键切图 → 8 片全部 ≤1MB（最大 930,553 字节），落 `out\测试长图\`，**目录里只有切片 JPG**，命名带图名前缀
- 再上传第二张（1200×6000）→ 尺寸与输出目录都切换；**旧预览块被回收**（临时目录里始终只剩 1 个，实测集合从 `…_h6tv6omu` 换成 `…_toa1h8ru`）
- 非图片扩展名 / 空请求体 → 明确中文报错；伪造 Host → 403；`/api/shutdown` → 进程正常退出

页面 JS 另用 jsdom 跑 23 项断言（切割线数、线样式一致、默认缩放 50%、`top%` 与 Y 严格对应、矮片警告、结果面板）—— 全通过。


## 六、界面瘦身：删掉片高输入与线条分级（2026-10-13 第三轮）

### 结论：这两块对出片零影响，已删除

`/api/slice` 的入参只有三样：人点的 `cuts`、`单片上限 maxSize`、以及 `cfg["min_h"]`
（后者只用于给矮片打 `under` 标记，**不改变切割位置**）。据此逐项核对 UI：

| 被删元素 | 原用途 | 对出片的影响 |
|---|---|---|
| 片高 min–max 输入框 | 给「自动识别切口」当参数；给矮片亮 ⚠ | **零** |
| 蓝线/橙线/灰虚线分级 + 说明文字 | 仅 CSS class，由 `rankCls()` 产出 | **零** |

用户的判断（「切图范围由人工选，与片高关联不大，也与线条类型无关」）在代码层面完全成立。
`grade_cuts()`（core）与 `rankCls()` / `bandWidth()` / `MAJOR_W`（页面 JS）随之成为死代码，一并删除。

### 删除后的等价行为

- 「自动识别切口」不再从 UI 取参，改由服务端回落 `cfg["min_h"]`（默认 1000）/
  `cfg["max_h"]`（默认 0 = 不限）——即前端直接 `post('/api/propose', {})`。
- 矮片 ⚠ 警告保留，阈值固定为注入的 `MIN_H`（默认 1000）。人手动落两条相近的线仍会被标出。
- 线条统一 `var(--ac)`（红，2px）；选中态仍为 `var(--pri)`（蓝，3px），
  靠**颜色 + 粗细**双通道区分，不会与普通线混。
- 片高下限仍可用命令行 `--min-h` 覆盖（只影响自动识别与警告阈值，不影响切割）。

### 验证

`test_ui_logic.js` 的断言随之改写：删掉「片高输入已读到 1000」「主/次刀数」等 4 条，
新增「片高输入框已移除」「颜色说明文字已移除」「所有切割线样式一致」「状态栏不再提主/次刀」。
「矮片警告」那条原先靠改 `#minh` 输入框触发，现改为直接驱动 `window.cuts` 造出 500/300px 的片——
**警告逻辑本身没变，只是触发方式不再依赖已删除的控件**。

### 附：预览默认缩放改为 50%（同日）

`DW` 原本兼具两义——既是「100% 时的宽度」，又被当作「初始宽度」直接 `setWidth(DW)`；
而 `__DZ__` 被写死为 `1`，所以初始必然落在 100%。两个含义纠缠在一起，改初值就必然算错。

现拆开：

- `DW` 只表示 **100% 时的显示宽度**（默认 = 源图宽度）
- `__DZ__` 表示 **初始缩放**，初值 `1` → `0.5`

| 位置 | 改前 | 改后 |
|---|---|---|
| 缩放按钮换算 | `DW * z[0] / DZ` | `DW * z[0]`（`DZ=1` 时两者等价，去掉冗余除法） |
| 初始化 | `setWidth(DW)` | `setWidth(DW * DZ)` |
| 高亮判定 | `z[0] === __DZ__` | 不变，自动落到 50% 那颗按钮 |
| `--display-width` | 「初始显示宽度」 | 语义不变：仍是 100% 时的宽度 |

实测：750px 宽的图初始显示 375px、`50%` 按钮高亮；三颗按钮分别给出 375 / 563 / 750px。
